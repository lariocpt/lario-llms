Flash alone preserves prefix-cache preferences and does not erase idle KV on

three complete windows, rejects a fourth and prevents coexistence with the

**No throughput claims**

Thread CPU must be recorded during baseline, idle, prefill, decode and concurrency
1/2/3 tests. Use `python3 arcB70/benchmarks/cpu_monitor.py --pid <native-pid>
--output <report-directory>/cpu.jsonl --phase <phase> --duration 60` alongside
each workload. Percentages use one logical CPU as 100%; aggregate can exceed
100%. Record active requests with latency and throughput before diagnosing
polling or a CPU bottleneck. On 2026-10-26 a five-second live sample showed the
existing B70 server main thread at 99.9%, other threads almost idle, with two
active requests. The cause is not yet established; no runtime tuning was applied.

Follow-up stack sampling located the hot main thread in Intel's Level Zero GPU
driver underneath SYCL/oneMKL flash attention. Three samples all traversed
`ggml_sycl_flash_attn_ext_mkl`; two included `urQueueFinish`. Together with the
near-100% userspace CPU sample, this points to active GPU synchronization/polling
in that attention path. It does not establish a throughput bottleneck or that
Flash Next's different attention path will behave identically. Samples are saved
as `research/benchmarks/20261026-b70-flash/current-qwen-cpu-stack.txt`.
Compare this signature during Flash Next testing before changing wait policies.

Deeper sampling: 11 of 12 snapshots traversed MKL attention synchronization
(eight `urQueueFinish`, three `urEventWait`; two included `__sched_yield`).
The pinned `fattn-mkl.cpp` uses 8192-token KV chunks. For each batch and KV head
it waits once before the chunk loop; each chunk then waits after dequantization
and, for each query tile, after KQ GEMM, softmax and VKQ GEMM. Thus one query
tile incurs four synchronization points per chunk, plus the initial wait.
Long KV spans multiply these waits. CPU spinning/yielding in the driver while
waiting for these GPU stages explains the hot main thread in the observed load.

The matching compute-runtime 26.35.39758.10 source has an initial polling phase
before eligible event waits can sleep; `PowerSavingMode` defaults to zero.
Its Linux user-fence KMD-wait flag is already true by default, so enabling that
flag blindly is not a justified fix. Wait eligibility and duration on this exact
path have not been measured. During an idle, controlled validation window,
compare the unchanged baseline against a verified low-power wait policy;
measure thread CPU, first-token latency, decode, power and output correctness.
Retain all required GPU dependencies. No environment, kernel or runtime settings
were changed for this investigation.

## Download without an AI session

Run `python3 -m arcB70.download_flash` from the repository to download and verify
all four pinned Q4 shards. `--verify-only` performs no network requests.
Completed shards are reused; the installed HF client restarts incomplete shards.
The user unit `b70-flash-download.service` waits for the existing transfer and
verifies completion, or takes over if that process stops. Check its status with
`systemctl --user status b70-flash-download.service` and its journal with
`journalctl --user -u b70-flash-download.service`. This job never loads models,
changes owner controls or calls an AI model. All four shards have completed and
passed SHA256 verification. Reboot acceptance remains pending.

## Strata runtime checks, 27 October 2026

The signed Strata SYCL engine 0.1.50 and its libraries are installed under
`~/.local/share/strata/components`; the prepared pack remains on XFS under
`/mnt/xfs/AI_Models/strata/packs/qwen38-flash-ud-q4-k-xl`.
`arcB70/strata/setup.py --prepare` reproduces acquisition and preparation.
The registry's earlier llama.cpp memory estimate is a separate, unvalidated
candidate and does not describe Strata's streaming allocations.

Real Q4-weight/Q4-KV inference passed at 32K and at one 262,144-token configured
slot. The 256K test loaded in 61.95 seconds. Its 19-token prompt returned the
correct answer twice: 24.05 seconds cold and 0.68 seconds repeated. These tiny
requests verify inference and warmup, not full-context quality or throughput.

Three 262,144-token slots were allocated with 2,210 MiB of reported VRAM free,
but the first request stalled in the 4-token GPU verify window at position zero.
The engine's watchdog stopped it; the harness restored the previous profile.
`STRATA_WINDOW_SYNC=1` did not resolve this failure. This is a runtime failure,
not evidence that a smaller context is required. Three working sessions and a
maximum usable three-slot context have not yet been established.

The same three-slot failure also reproduced at 32K (no KV streaming), and in
an unpatched B70 AOT build of official pinned source, engine 0.1.51. The build
recipe is `arcB70/strata/build-b70.sh`; it keeps source, build products and
checksum-verified private Intel SYCL development headers under the app directory.
The signed engine is preserved. Build SHA256:
`ada2d6135cdd8272e4ab3d6e3a82001dbfc0f7f1721fce2c07ac7263918c30bd`.
The diagnostic `STRATA_VERIFY_NO_HOST=0` made progress to layer 7 but still
stalled and failed; it is not a validated workaround. A batched-prefill-only
attempt (`--short-read 0`) made no inference progress and was terminated by the
operator after roughly three minutes; restoration succeeded.

Raw commands, engine metadata, timing results and telemetry are in
`research/benchmarks/20261027-b70-flash/`. The bounded smoke harness supports
repeated prompts, concurrent slots, prompt files and first-token timing, and
refuses to unload active owner/native work. The Flash profile remains disabled
and is not published into live OpenCode configurations until it passes.
